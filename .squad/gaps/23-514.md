# Gaps — Plan 23 / Story 514 (demo data seeders)

Things found while building this story that the plan does not describe.

The pattern of this one is worth naming: **a seeder that fills every column is
a test of every screen that reads them.** Three defects below had been live for
several stories and were invisible because every ticket anyone had ever created
— by hand or in a fixture — had a null assignee and a null category.

---

## 1. The ticket list shipped ids with no way to render them

`TicketListTable` takes `assigneeNames` and `categoryNames` maps. They were
optional props defaulting to `{}`, and **no page ever passed them**. So the
Assignee and Category columns rendered a dash on every row of the busiest
screen in the product — an assigned ticket looked exactly like an unclaimed
one.

The client could not have fixed it for itself: `/users` and `/admin/categories`
are both behind capabilities an ordinary agent does not hold.

Fixed:

- `TicketsController::index` side-loads `included.assignees` and
  `included.categories` for the ids on the page — one query each, via the
  `AssigneeDirectory` that already existed for exactly this in
  `TicketEventsController`.
- Category labels are localised server-side from the reader's own
  `preferred_locale`.
- `AgentHomeScreen` and `TicketListScreen` now read the maps off the same
  response the rows came from, and the never-supplied props are gone.
- `TicketListCarriesTheNamesItNeedsTest` (4 cases) and
  `TicketListNames.test.tsx` (2 cases). The frontend pair was confirmed to
  fail when the wiring is reverted.

---

## 2. `/ticket-categories` and `/assignees` did not exist

`TicketDetailPage` has fetched both on mount since the ticket workspace
shipped. Neither route was ever added. Both 404ed on every page load, and the
page swallows a reference-data failure **on purpose** — a select with no
options is a smaller problem than a workspace that will not open.

The swallow is right. What was missing is anything that noticed the options
were ALWAYS empty. The Category and Assignee selects on the ticket workspace
have never worked: an agent could not see who held a ticket, and could not
move it.

Fixed: `TicketReferenceDataController` with both endpoints, gated on
`ticket.read` rather than on managing the underlying lists — an agent who may
not edit the category list still has to pick from it. Deactivated accounts are
not offered, because `AssignTicket` refuses them anyway and the option could
only ever produce an error. `TicketWorkspaceReferenceDataTest`, 5 cases.

---

## 3. Every seeded reply was marked as a failed delivery

`email.enabled` defaults to `false` — deliberately, so a fresh install cannot
mail real customers on boot. That meant every outbound message the seeder
wrote went through `SendAgentReply`, came back
`MailTransportFailure: The email channel is switched off`, and was recorded
`delivery_state = failed`, leaving 18 rows in `failed_jobs`.

The visible result: a red **"Not sent — this reply did not reach the
customer"** on every single agent reply in the demo dataset.

Neither the send nor the failure ever happened. Seeded messages are a story
about the past; nobody pressed Send. The seeder now suppresses
`AgentReplyPosted` around the build (`Event::fakeFor`, so the dispatcher is
restored afterwards) — the same reasoning as `suppressAcknowledgement`.
Asserted by `test_no_seeded_reply_claims_it_failed_to_reach_anybody`.

**Still open, and not this story's to fix:** a disabled channel and a real
bounce both land in `delivery_state = failed`. Once somebody turns email on,
they cannot tell the two apart in the history. This is the same conflation the
attachment scanner explicitly refused to make — there, `unreachable` keeps its
own state precisely so an outage never reads as a verdict. Outbound mail should
do the same.

## 4. `migrate:fresh` does not reset the ticket reference sequence

`ticket_reference_seq` is created with `CREATE SEQUENCE IF NOT EXISTS`, and
Laravel's `migrate:fresh` drops tables, views and types on Postgres — not
sequences. So a freshly migrated database keeps counting from wherever the
previous one stopped: the first ticket after a rebuild here was `TKT-000043`,
then `TKT-000061`.

Harmless — references never collide, which is the property that matters, and
the continuity test passes. But a "fresh" database is not fresh in this one
respect, and anyone debugging a reference will be surprised by it. Left alone
deliberately: changing reference allocation to satisfy tidiness is a worse
trade than the surprise.

---

## 5. Nothing sets the application locale per request

`app()->getLocale()` is always the config default. No middleware reads
`Accept-Language` or the signed-in person's preference, so any `__()` in an API
response is English regardless of who is reading.

Notifications escape this because `HasLocalePreference` makes Laravel wrap each
send in the recipient's language. Everything else does not. Both new pieces of
localised API output here (`included.categories`, `/ticket-categories`) read
`$request->user()->preferredLocale()` explicitly for that reason — which works,
and is a workaround for something that should be middleware.

## 6. Deviations from the plan

- **`Actor::staff($id, $name)`, not `new StaffActor($user)`.** The plan's call
  shape does not exist; the factory takes primitives so the domain never holds
  a `User`.
- **`CustomerState::Inactive`, not `DEACTIVATED`;** `Category` uses
  `name_en` / `name_ar` / `sort_order` with no `is_active` column; departments
  have no code column. The plan named columns this schema does not have. The
  repo's own vocabulary won each time.
- **Customer references come from `Customer::mintReference()`,** which is a
  random Crockford-alphabet mint, not a sequence allocator. The plan assumed an
  injectable allocator; there is none, and the natural key for idempotency had
  to be the primary email identifier instead of the reference. Asserted by
  `test_a_customer_reference_is_minted_not_written`.
- **A shared `DemoEnvironment` guard** rather than the environment `if` copied
  into seven files. Seven copies is seven chances to write `!== 'production'`,
  which allows staging.
- **`callOnce`, not `call`, for dependencies.** Seven seeders each naming their
  own left `DemoDepartmentsSeeder` running twelve times in one full seed.
- **`scripts/restart.sh` no longer uses `migrate:fresh --seed`.** Seeding is its
  own step on all three paths, so a seed failure is reported as a seed failure
  rather than as part of a migration that succeeded. Verified by deliberately
  throwing inside a seeder: the script aborted with `SEED_FAILED`, printed the
  tail of `.run/seed.log`, and exited 1.
- **`php artisan db:counts`** as a real read-only command rather than the
  inline `tinker --execute` the plan suggested — it is testable, and it is
  useful outside the script.

## 7. `callOnce` remembers the process, not the database

The dependency calls were `callOnce` at first, to stop
`DemoDepartmentsSeeder` running twelve times per full seed. `Seeder::$called`
is a static, so it survives a database reset — and
`DemoAttachmentsSeeder` run on its own, in a process that had already seeded
once, skipped every dependency, found no ticket to attach to, and **reported
success having written nothing**.

Caught by `DemoSeedersRunInIsolationTest`, which was written for the plan's
"runnable in isolation" criterion and failed on its first run.

Replaced with `DemoEnvironment::needs($seeder, $class, $satisfied)` — run the
dependency unless its rows are already there. Asking the database is the
question that actually matters, and it costs one `exists()`.

---

## 8. The customer's first message shows twice in the portal

Visible on any email-originated ticket. `InboundMailIntake::openTicket` sets
`description = $mail->body` and then appends an inbound message with the same
body, so the portal thread renders the customer's own words twice in a row.

**Not a seeder artifact** — the seeder reproduces production faithfully, which
is how it surfaced. Portal-created tickets are unaffected, because
`CustomerRequests::submit` writes only the description.

Not fixed here: the repair belongs either in the email intake (do not duplicate
the body) or in the portal detail (do not render the description separately
when the first message repeats it), and choosing between them is an Email/
Portal decision, not a seeding one.

## 9. Not verified

The plan's frontend smoke test (step 11) was walked in a real Chrome against
the seeded stack: agent home, ticket list, a ticket detail (properties,
conversation, internal-note badge, customer panel), the customer list, the
admin Organisation and Ticketing screens (five bilingual categories rendering
Arabic correctly), and the portal signed in as a seeded account — four
requests, no internal note, no agent named.

**Not walked by hand:** the audit log, service levels, email and platform admin
sections; and downloading an attachment through the interface. The download
path itself is proven end to end by `SeededAttachmentsDownloadTest`, which
follows the signed redirect and checks the bytes.
