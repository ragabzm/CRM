# ثغرات لقيتها أثناء ستوري 14 / 505

حاجات مكسورة أو ناقصة **مش** موصوفة في `14-story-505.md`.

## 1. 🔴 تسريبة: محادثة التذكرة كانت مقروءة لأي وكيل

`GET /api/v1/tickets/{id}/messages` **ماكانش بيطبّق `TicketVisibility` خالص**.

`can.capability:ticket.read` على الراوت بيقول إن الوكيل مسموح له يقرا تذاكر —
مش إنه مسموح له يقرا **التذكرة دي**. النتيجة إن أي وكيل بأي صلاحية قراءة كان
يقدر يجيب المحادثة كاملة لتذكرة مخصّصة لزميله بمجرد إنه يعرف الـ ULID.

**اتأكدت منها بـ probe فعلي قبل ما أدّعيها:**

```
GET /api/v1/tickets/{id}          →  404   (صح)
GET /api/v1/tickets/{id}/messages →  200   leaked=YES
```

`show` كان بيطبّق القاعدة صح، `messages` لأ. ونصوص الرسائل هي أكتر حاجة حسّاسة
التذكرة بتشيلها.

**اتصلحت.** `assertVisible()` على `index` و`store` — القراءة والكتابة. الكتابة
كمان لأن إنك تكتب في تذكرة مش شايفها هي نفس التسريبة خطوة أبعد: بتحطّ كلامك في
محادثة حد تاني.

مغطّاة بـ `TicketMessageVisibilityTest` (٥ تستات).

**الدرس:** القاعدة موجودة في مكان واحد صح (`TicketVisibility`)، بس مفيش حاجة
بتفرض إن كل نقطة بتقرا محتوى تذكرة تنده عليها. النقطة الجديدة (`/events`)
بتطبّقها من أول يوم، بس الحارس ده لسه مش موجود.

## 2. ⚠️ الـ REVOKE على `ticket_events` **مابيعضّش** في البيئة الحالية

الخطة طلبت `REVOKE UPDATE, DELETE, TRUNCATE`. اتعمل، و`information_schema`
بيقول إنه اشتغل:

```
ragab | INSERT, REFERENCES, SELECT, TRIGGER
```

**بس التعديل والحذف لسه شغّالين:**

```
update ticket_events set event_type='rewritten';  →  UPDATE 1
delete from ticket_events;                        →  DELETE 1
truncate ticket_events;                           →  TRUNCATE TABLE
```

السبب: `ragab` دوره **superuser** (`rolsuper = t`)، والسوبريوزر بيتخطّى كل فحص
صلاحيات في Postgres.

ده **أسوأ من إننا مانعملش revoke أصلاً**، لأن الدليل اللي أي مشغّل هيروح
يبصّ عليه (`information_schema`) بيقول إن التاريخ محمي وهو مش محمي.

**اللي عملته:** الميجريشن بقى بيكتشف الحالة دي ويطلع تحذير صريح فيه العلاج:

```
[WARNING] ticket_events: UPDATE/DELETE/TRUNCATE were revoked but will not be enforced.
  reason: The application connects as a PostgreSQL superuser, which bypasses every privilege check.
  remedy: Run the application as a non-superuser role…
```

**مطلوب عند النشر:** التطبيق يتصل بدور **مش سوبريوزر**. لحد ما ده يحصل، حماية
التاريخ على مستوى قاعدة البيانات هي الـ CHECK constraint بس.

الـ CHECK constraint **بيشتغل فعلاً** — متأكد منه، والسوبريوزر مابيتخطّاهوش
لأنه قيد مش صلاحية:

```
insert … actor_type='system', actor_id='7' →
ERROR: violates check constraint "ticket_events_system_actor_check"
```

## 3. شكل الـ payload كان متضارب بين مسارين

`UpdateTicketAttributes` كان بيكتب `{before, after}` في مسار و
`{attribute, from, to}` في المسار التاني. يعني اللوحة اللي هتقرا التاريخ
(ستوري 4.4) كان لازم تعرف نوع الحدث **قبل** ما تعرف تلاقي القيم فين.

وكمان `before`/`after` كانوا بياخدوا **كل** القيم المتنازع عليها مش اللي اتغيّر
بس — وده مخالف لبند صريح في معايير الخطة.

اتوحّدوا على `{before, after, meta}` لكل الأنواع، وبالمتغيّر بس.
`TicketEventsAppendOnlyTest` + `TicketEventRecorderTest` بيفرضوا ده.

## 4. حارس الترانزاكشن مش قابل للاختبار تحت `RefreshDatabase`

`TicketEventRecorder` بيرفض يكتب برّه ترانزاكشن — وده الميكانيزم اللي بيمنع
التاريخ يبقى فيه فجوة.

بس `RefreshDatabase` بيلفّ كل تست في ترانزاكشن، يعني `transactionLevel()`
بيبقى 1 قبل ما التست يعمل أي حاجة. **الحارس مستحيل يشتغل في أي تست عادي.**

اتحل بتست على اتصال stub بيرجّع 0. مسجّل هنا لأن نفس الفخ هيتكرر مع أي حارس
تاني بيقرا حالة الاتصال.
