# Gaps found while implementing Story 7.3 (Azure #523)

## The test suite cannot see CSRF at all

`Illuminate\Foundation\Http\Middleware\PreventRequestForgery::handle()`
short-circuits when `runningUnitTests()`, so **no test in this repository can
exercise CSRF**. Every request in the suite passes the check regardless of
whether it would pass in a browser.

This is not theoretical. It has now produced the same defect twice in two
consecutive stories, both found only by opening a browser:

- Story 11.1: the emailed-feedback comment box returned **419** while the
  rating, recorded by the link's GET, looked fine — so a customer wrote a
  sentence, pressed save, and was told nothing worked.
- Story 7.3: the chat widget returned **419** on every message a visitor sent.
  Twenty-six server tests passed against the same code.

Both are fixed in their own stories. What is not fixed is the blind spot: any
future endpoint that carries a cookie and is called cross-site will ship broken
and green.

Worth considering, none of which belongs to this story:

- A test-only middleware alias that runs the real `PreventRequestForgery`, so
  at least one test per cookie-carrying surface proves the shape works.
- A smoke test against a booted server rather than the test kernel.
- A lint rule over `routes/api.php`: a route group that reads a cookie and is
  not in the CSRF `except` list is either wrong or needs a comment saying why.

## The chat widget depends on third-party cookies

The visitor's token is an http-only cookie, because AC-3 forbids `localStorage`
and `sessionStorage` and AC-12 requires a reload to rejoin the same
conversation. In a third-party embed that is a third-party cookie
(`SameSite=None; Secure`).

Verified working in Chrome today, from a genuine second origin
(`http://localhost:4173` embedding `http://localhost:3000`). It will stop
working in browsers that block third-party cookies outright — Safari already
does by default.

The degradation is graceful and was chosen deliberately: a visitor whose cookie
is blocked starts a fresh conversation after a reload instead of rejoining. They
lose nothing they typed, because the previous conversation is already a ticket
with the full transcript. Recorded here because it is invisible until it
happens, and because the fix — a token in the URL fragment, or the Storage
Access API — is a decision about the widget's shape rather than a bug in it.
