# Gaps — Plan 22 / Story 513 (My requests)

Things found while building this story that the plan does not describe.

---

## 1. Internal notes could not be saved on Postgres — at all

`ticket_messages_direction_check` was written in Story 4.1 (`2026_09_05_000400_create_ticket_messages_table.php:56`) allowing exactly
`inbound` and `outbound`. Story 4.4 added `internal` to the enum, the model,
the composer, the API and the interface — and nobody touched the constraint.

Every attempt to write an internal note on a real database was refused:

```
new row for relation "ticket_messages" violates check constraint
"ticket_messages_direction_check"
DETAIL: Failing row contains (..., internal, staff, ...)
```

So the internal-note feature shipped in Story 4.4 has never worked outside the
test suite.

**Why no test caught it.** The constraint is added under a
`DB::getDriverName() === 'pgsql'` guard. The suite runs on in-memory SQLite,
where that branch never executes — so every test about internal notes ran
against a table that had no such rule. The tests were not wrong; they were
checking a schema production does not have.

This is the fifth instance of the same shape in this project, and the second
of this exact one (`drop_reopened_status`, Story 504, was the first).

Fixed here:

- `2026_09_15_000100_allow_internal_message_direction.php` rebuilds the
  constraint with all three values.
- `tests/Feature/Tickets/MessageDirectionConstraintPostgresTest.php` connects
  to a real Postgres, migrates fresh, and asserts the constraint text contains
  every `MessageDirection` case. Adding a fourth direction without a migration
  now fails there instead of in production. It **skips loudly** when Postgres
  is unreachable rather than passing silently.

**Still open, and bigger than this story:** every other `pgsql`-guarded
`DB::statement` in the migrations is invisible to the suite for the same
reason. The general fix is a CI leg that runs the suite against Postgres, not
one test per constraint. Worth its own story.

## 2. The query layer went to Tickets, not Portal

The plan asks for `MyRequestsQuery` **inside the Portal module**, scoping every
query by `auth('portal')->user()->customer_id`.

That cannot be built. Portal is T4 and Tickets is T3; a query object in Portal
would have to name `Tickets\Domain\Ticket`, which deptrac refuses, and
`OnlyTicketsModuleMutatesTicketsTest` refuses independently.

Built instead, following this repo's established contracts-with-the-consumer
pattern (`SlaReader`, `CategoryUsageProbe`):

- `Tickets\Contracts\CustomerRequestGateway` — five methods, primitives only,
  **every one takes `customerId` as its first argument** so scoping is not
  something a caller can forget.
- `Tickets\Application\Portal\CustomerRequests` — the implementation, owned by
  the module that owns the rows.
- `Portal\Http\Controllers\PortalRequestsController` — reads
  `customer_id` off the guard and passes it in; knows nothing else about
  tickets.

The absolute data boundary the plan wanted still exists. It just lives on the
side of the wall that owns the data.

`tests/Architecture/PortalReachesTicketsThroughContractsTest.php` pins it.

## 3. Problem-details identifier follows the repo, not the plan

Plan: `type=urn:problem:reopen-window-expired`.
Repo: `module.condition` codes throughout, so this is
`tickets.reopen_window_expired`.

Changing one refusal to a `urn:` scheme would leave the API with two
vocabularies. The repo's own convention won.

The extension the plan actually depends on — `new_request_url` — is present and
tested (`PortalReopenTest`).

## 4. Test files consolidated, not one-per-scenario

The plan names sixteen test files. What exists is the same coverage in five:
`PortalRequestsTest` (16 cases), `PortalReopenTest` (9),
`PortalRequests.test.tsx` (16), `a11y/portal.test.tsx` (18), and
`PortalReachesTicketsThroughContractsTest`.

Every numbered scenario in the plan has a case. Splitting them across sixteen
files would have meant sixteen identical fixture setups.

## 5. Every browser-side API call was blocked by CORS

Found by walking the portal in a real Chrome, which is the only way it could
have been found.

Sign-in showed "Something went wrong. Try again." The API log showed a clean
`204`. The browser showed `net::ERR_FAILED` on `/sanctum/csrf-cookie`.

There is no `config/cors.php` in this repo. Laravel ships `HandleCors` in the
global stack and falls back to `allowed_origins => ['*']` with
`supports_credentials => false`. This is a session-cookie API — every call
from the SPA carries `credentials: "include"` — and a browser refuses BOTH of
those on a credentialed request: the wildcard is rejected outright, and
without `Access-Control-Allow-Credentials: true` the response is discarded
before any JavaScript sees it.

So the header that looked maximally permissive was, in practice, a closed
door. **Nothing that fetches from the browser could work** — not the portal,
not the staff app. Only server-rendered calls, which do not go through CORS,
have ever worked.

**Why the suite could not see it.** `$this->get()` is not a browser. It sends
no `Origin`, performs no preflight, and enforces no CORS rule. 1021 tests
passed against a configuration no browser would accept. This is the same
shape as the four earlier findings — a test that never touches the layer the
bug lives in — but the widest one so far.

Fixed here:

- `config/cors.php` — named origins from `CORS_ALLOWED_ORIGINS`,
  `supports_credentials => true`, `sanctum/csrf-cookie` in `paths`, and
  `ETag` / rate-limit headers exposed so the client can read them
  cross-origin.
- `tests/Feature/Security/CorsAllowsTheBrowserToSendCookiesTest.php` — sends
  the `Origin` a browser sends and asserts what a browser checks: exact origin
  echo, never `*`; credentials allowed; preflight answered for a JSON +
  `Idempotency-Key` write; an unknown origin NOT echoed; `ETag` exposed.

Confirmed to catch it: with `config/cors.php` removed, 6 of the 7 cases fail.

## 6. The Docker stack serves a build from 28 hours ago

Neither `frontend` nor `backend-web` mounts source — both are baked images
(`build: ./frontend`, `build: ./backend`; the frontend container holds only
`server.js` and `node_modules`, with no `app/` directory at all). The
containers had been up 28 hours, so the running stack predates roughly ten
stories. `/portal/sign-in` returned 404 on `localhost:3000` while the route
existed on disk and every test for it passed.

This is why the CORS bug survived: the only stack anyone runs locally has been
serving code old enough not to have the portal in it.

The walkthrough was done against `pnpm dev` and `php artisan serve` on the
host. **The containers still need `docker compose build` before the Docker
stack reflects the current code** — worth adding a dev-mode source mount so
this cannot silently recur.

## 7. Mobile is asserted at 320 px, but not on a real handset

Walked in a real Chrome under mobile emulation (320x640, touch, an iOS Safari
user agent), against `pnpm dev` and `php artisan serve`:

- sign in -> list -> open a request -> submit a new request -> reply, all
  completed;
- `documentElement.scrollWidth === clientWidth === 320` on the list, the
  detail and the new-request form, with zero elements extending past the
  viewport;
- the detail leaks no internal note, no agent name, and no SLA text;
- the file input carries `capture="environment"`,
  `accept="image/*,application/pdf"`.

What is **still not verified**: whether the camera actually opens. `capture`
is a hint, honoured differently by iOS Safari and Android Chrome, and
emulation has no opinion on it — a spoofed user agent is not WebKit. Note
also that `accept` mixes `application/pdf` with `image/*`; iOS Safari is known
to ignore `capture` for some non-media accept lists, so the camera may or may
not be offered on a real iPhone.

Two smaller things the emulated pass showed, neither a blocker: the header and
nav tap targets measure 22-29 px tall, under the 44 px both Apple and Google
recommend for a thumb.

Still needs a real iOS Safari and a real Android Chrome, same standing gap as
Story 495 and Story 506. Cannot be closed from a terminal.

## 8. Fixed in passing

- **`SegmentedFilter` submitted the form it sat in.** Its `<button>` had no
  `type`, so it defaulted to `submit`. Any instance inside a `<form>` — the
  portal filter is — submitted on click. Added `type="button"`.
- **The version guard refused every portal reopen** with
  `tickets.stale_version`. A customer has no version to be stale against; the
  exemption in `UpdateTicketAttributes` now covers `portal` alongside `system`.
- **`customers.department_id` was NOT NULL**, which blocked the customer rows
  auto-created from inbound email (Story 5.2) from ever being linked to a
  portal account. Made nullable
  (`2026_09_11_000400_allow_customers_without_a_department.php`).
