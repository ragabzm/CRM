# Gaps found while building 12.3 (Azure #536)

## 1. Secret settings were never encrypted at rest

**Found:** Story 12.3's AC-12 asks for credentials "write-only through the console,
encrypted at rest, never logged and never returned by any endpoint." Three of those four
already held. **Encryption at rest did not.** `SettingsRepository::upsert` wrote every
value as plain JSON regardless of `SettingDefinition::$secret`, which was only ever
consulted to mask values on the way *out* (`redactedValue()`).

This is not new to this story. It affected every secret shipped before it:

- `email.provider_credential`
- `email.inbound.webhook_secret`
- `email.mailbox.password`
- `email.mailbox.username`

Anyone with a copy of the database — a dump, a read replica, last night's backup tape —
had the mail provider's credential in plaintext. The console was careful; the storage
was not.

**Fixed in this story.** `SettingsRepository` now seals secret values in a
self-describing envelope (`{"__encrypted": "<ciphertext>"}`) and unseals on read.
Self-describing because `all()` and `find()` read *rows*, not settings, and have no
definition to consult — a scheme where the reader must already know which keys are
secret decrypts the wrong thing the first time a key is renamed.

Covered by `ErpAdapterTest::test_a_credential_is_encrypted_at_rest`.

**Still outstanding — deliberately:** a row written *before* this change stays plaintext
until it is next saved. `decode()` reads both forms, so nothing breaks, but an existing
deployment's mail credential is not retroactively encrypted. Re-saving each secret in the
console fixes it. A migration was not written because it would have to instantiate the
settings registry to know which keys are secret, and a migration that boots application
services is a migration that fails on a half-deployed release.
