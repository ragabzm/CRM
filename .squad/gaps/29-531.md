# Gaps found while implementing Story 10.3 (Azure #531)

## The frontend test suite reports machine load as test failures

Running `pnpm test` (vitest 4.1.11, forks pool, default worker count) on a
loaded machine produces output that is indistinguishable from real breakage:

```
 Test Files  9 failed | 91 passed (100)
      Tests  13 failed | 886 passed | 84 skipped (983)
Error: [vitest-pool]: Failed to start forks worker for test files …
Caused by: Error: [vitest-pool-runner]: Timeout waiting for worker to respond
```

Individual tests are reported as failing with 303s durations — the per-test
timeout — including trivially fast ones (`EmptyState has no violations 1ms`).
Nothing in the summary line says the workers never started.

Measured: with the Docker stack up and macOS background daemons churning (load
average 38–68), the run took 996s and reported 36 failures. With Docker stopped
and `--maxWorkers=2`, the same commit passed **103 files / 1003 tests** in a
normal time. No code changed between the two runs.

Consequence: `scripts/verify.sh` can fail on a busy machine and name specific
tests that are fine, which sends whoever reads it looking for a bug that is not
there. It can also do the reverse in CI — a flaky agent under load looks like a
real regression and gets "fixed".

Not addressed here because the right fix is a decision about the test runner,
not about this story: cap workers in `vitest.config.ts`, switch the pool to
`threads`, or raise the worker start timeout. Any of the three needs measuring
against CI's own machine shape.
